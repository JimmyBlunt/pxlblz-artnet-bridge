## 2. Was v0.3 ändert

```text
                 ┌── WS input (PXLBLZ) ──┐   oder   ┌── Pattern-Generator ──┐
                 └───────────┬───────────┘          └───────────┬───────────┘
                             ▼                                  ▼
                      LatestFrame (ein Slot, keine Queue)
                             │
      ┌──────────────────────┼──────────────────────┐
      ▼                      ▼                      ▼
 WS2812_NODE_244        PANEL8_251            BACK_PANEL_249 (.253)
 eigene Goroutine       eigene Goroutine      eigene Goroutine
 60 fps, eigene Seq     30 fps, eigene Seq    30 fps, eigene Seq
 1 Snapshot → Burst     1 Snapshot → Burst    1 Snapshot → 29 Universen
```

### 2.1 Config v2 (v1 bleibt gültig)

```json
{
  "version": 2,
  "input": {"pixel_count": 8186, "fps_target": 60,
            "stale_timeout_ms": 2000, "on_stale": "hold"},
  "controllers": [
    {"name": "WS2812_NODE_244", "target_ip": "10.0.0.244", "fps_target": 60},
    {"name": "BACK_PANEL_249",  "target_ip": "10.0.0.253", "fps_target": 30, "enabled": true}
  ],
  "routes": [ … wie bisher … ]
}
```

- `controllers[]` ist optional. Fehlt es, wird pro Ziel-IP automatisch ein Controller mit `input.fps_target` angelegt. Damit verhalten sich alle v1-Configs wie bisher.
- Wenn `controllers[]` gesetzt ist, muss jede aktive Route eine passende `target_ip` haben.
- `enabled: false` auf einem Controller schaltet alle seine Routen ab.
- `stale_timeout_ms` / `on_stale`:
  - `hold` (Standard) sendet das letzte Bild weiter (Verhalten wie v0.2),
  - `blackout` sendet Schwarz,
  - `stop` sendet nichts, bis wieder Input kommt.
- Vor dem **ersten** gültigen Frame wird nie gesendet (wie in v0.2).
- Beim Start gibt es Warnungen, wenn sich die logischen Pixel zweier Routen überlappen oder ein Controller keine Routen hat.

### 2.2 Controller-Ebene im Router

- `Controller` besitzt Sequenz, Paketpuffer und Statistik. Die Sequenz wird erst erhöht, wenn der **ganze Controller-Frame** gesendet ist, und springt beim Überlauf von 255 auf 1, nie auf 0.
- `SendFrame()` (alle Controller) funktioniert unverändert. `SendController()` ist neu.

### 2.3 Scheduler (`internal/scheduler`)

- Jeder Controller läuft mit eigenem Ticker. Pro Tick nimmt er **einen** Snapshot aus dem LatestFrame und sendet daraus alle seine Universen.
- Controller warten nicht aufeinander und bauen keine Queue auf.
- `--fps N` setzt alle Controller auf N (für Tests).

### 2.4 Pattern `panel-walk` (für G9, ohne PXLBLZ)

- Alle Routen leuchten schwach in ihrer Port-Farbe: P1 rot, P2 grün, P3 blau, P4 cyan, P5 magenta, P6 gelb, P7 weiß.
- Die ersten 3 Pixel jeder Lane sind heller. Sie markieren den elektrischen **Anfang** und damit die Richtung.
- Ein weißer Kopf mit farbigem Schweif läuft in Config-Reihenfolge durch alle Routen (P1 → … → P7).
- Die Helligkeit ist bewusst niedrig: Hintergrund 6/255, Kopf 160/255.
- `--walk-speed` steuert die Geschwindigkeit (Pixel pro Frame, Standard 4 → ca. 34 s pro Runde auf BACK_PANEL).

### 2.5 Status-Endpunkt

`GET http://127.0.0.1:9988/status` liefert JSON mit RX-Zählern, dem Alter des letzten Frames, WS-Clients und
pro Controller Frames, Pakete, Fehler, Wiederholungen, Stale-Flag, Sendezeiten und die erwartete Universen-Liste.
CORS ist offen, damit eine spätere PXLBLZ-Output-UI (G11) die Daten direkt lesen kann. Mit `--status-listen ""` wird der Endpunkt abgeschaltet.

## 6. Entkopplung von parallel laufender Arbeit auf `main` (ab 2026-09-26)

Auf `main` wird parallel weiterentwickelt (u. a. virtueller Teensy-Controller,
Receiver-Probe, Änderungen in `router.go` / `config.go`). Damit sich v0.3 und diese
Arbeit nicht gegenseitig stören, gilt bis zum Abschluss von V1–V4:

1. **Feste Basis.** v0.3 zieht `main` **nicht** mehr nach. Basis ist `main@04eba84`
   plus die bereits übernommenen Lab-Fixes. Ein einziger Integrations-Merge mit `main`
   folgt erst, wenn V1–V4 bestanden sind; danach laufen die Software-Tests einmal neu.
2. **Keine EXEs im Branch.** `bin/windows-x64/` wird auf diesem Branch nicht mehr
   aktualisiert (die CI auf `main` baut und committet die EXEs selbst — jeder Commit dort
   erzeugt sonst einen sicheren Binär-Konflikt). Test-EXEs für die Hardware werden
   außerhalb des Repos gebaut: `PXLBLZ_ArtNet_Handoff_2026-09-26\v0.3-test-bin\`
   (mit `SHA256SUMS.txt` und `SOURCE_COMMIT.txt`). Beim Integrations-Merge gewinnt
   `bin/` von `main`, die CI baut danach neu.
3. **Tests gegen den eigenen Stand.** Soak- und Reservetests messen nur v0.3.
   Lokale Test-Ports des Performance-Labs sind über `--udp-port` / `--ws-port`
   verschiebbar, falls auf demselben PC parallel getestet wird.
4. **Umgekehrt** (Empfehlung für die parallele Arbeit): eigene Feature-Branches statt
   direkter Pushes auf `main`; Änderungen am Router-Kern (`internal/router`,
   `internal/config`, `cmd/pxlblz-router`) möglichst erst nach dem v0.3-Merge.
